# PostgreSQL Production-Grade Performance Tuner (AST Core)

본 프로젝트는 **PostgreSQL 데이터베이스**의 실제 실행 계획(Explain Plan)과 SQL AST(Abstract Syntax Tree) 분석을 결합하여, 성능 병목 구간을 진단하고 지식 기반의 맞춤형 인덱스 및 설정 튜닝 가이드를 자동으로 제공하는 데스크톱 애플리케이션입니다.

---

## 📌 주요 핵심 기능 (Key Features)

- **실제 실행계획(Raw Plan) 최상단 탑재**: DB 옵티마이저가 수립한 표준 텍스트 기반 트리 구조의 실행 계획을 리포트 최상단에 직관적으로 시각화하여 튜닝 신뢰성을 높입니다.
- **SQL AST 분석 기반 지식 매핑**: `sqlglot` 파서를 통해 SQL의 논리적 구조를 완전히 분해(AST)하여, 테이블 별칭(Alias) 및 조건절에 사용된 컬럼 정보를 정확히 타겟팅합니다.
- **시스템 카탈로그 교차 검증**: 단순히 쿼리문만 파싱하는 것에 그치지 않고, `pg_class`, `pg_index` 등 데이터베이스 시스템 카탈로그를 실시간 조회하여 인덱스 구성 상태 및 실제 데이터 테이블 크기(Row Count)를 고려한 정밀 휴리스틱 진단을 수행합니다.
- **안전한 온디맨드(On-Demand) 트랜잭션**: 분석 버튼을 누르는 즉시 연결을 맺고 완료 즉시 차단하며, `Explain (Analyze)` 등으로 인한 미세한 데이터 변경 가능성을 방지하기 위해 강제 롤백(Rollback) 세션 구조를 채택했습니다.
- **스마트 주석 처리(Comment Stripper)**: 한 줄 주석(`--`) 및 인라인 블록 주석(`/* ... */`)이 섞여 있는 대용량 실무 쿼리도 에러 없이 완벽하게 정제하여 처리합니다.

## 🔄 핵심 아키텍처 및 내부 동작 흐름

애플리케이션이 실행되고 분석 결과가 나오기까지 내부 구성요소들은 아래와 같은 라이프사이클을 가집니다.

1. **사용자 입력 및 단축키 수신**: 사용자가 SQL 편집창에 주석이 포함된 쿼리를 기입하고 `Ctrl + Enter` (macOS: `Cmd + Enter`) 혹은 하단 버튼을 클릭합니다.
2. **온디맨드 커넥션 및 주석 정제**: `PGPlanAnalyzer`가 정규식을 통해 주석 코드를 지워 순수한 쿼리 바디를 추출하는 동안, `psycopg.connect()` 세션이 타임아웃 제한(`connect_timeout=5`)을 걸고 DB에 긴급 접속합니다.
3. **실행계획 이중 분석 (TEXT & JSON)**:

- 옵티마이저로부터 텍스트 포맷의 날것의 실행 계획(Explain Text)을 추출하여 UI 상단에 트리로 즉시 배치합니다.
- 정밀 수치 진단을 위해 `ANALYZE` 옵션이 추가된 JSON 형식 실행 계획을 백그라운드에서 교차 수집합니다.

4. **AST 컬럼 분석 & 메타데이터 매핑**: `sqlglot` 엔진이 쿼리를 AST 노드로 파싱하여 실질적으로 조인 및 필터링(Where) 대상이 된 컬럼을 식별합니다. 이후 해당 테이블의 인덱스 구성 정보를 PostgreSQL 카탈로그 백엔드에서 조회해 매칭 상태를 논리적으로 연산합니다.
5. **휴리스틱 튜닝 제안서 생성**: 분석된 노드가 `Seq Scan`인 경우 인덱스 유무와 선택도(Selectivity)를 검증하고, `Sort` 노드의 경우 임시 디스크 소트 여부를 체크하여 최적의 교정 솔루션과 가이드라인 DDL을 화면에 출력합니다.
6. **세션 롤백 및 연결 Close**: 분석 전용 트랜잭션의 특성을 고려하여, 혹시 모를 내부 쓰기 동작을 완전히 무력화하기 위해 `rollback()`을 수행하고 Context Manager(`with`)를 통해 커넥션을 완벽히 해제합니다.

### 🔄 3-Way 하이브리드 교차 검증 아키텍처

이 도구는 작성하신 쿼리가 성능 문제를 일으키는지 진단하기 위해 아래 **3가지 데이터 원천**을 유기적으로 대조합니다.

```
                  ┌──────────────────────┐
                  │   1. SQL AST Tree    │
                  │ (필터링 대상 컬럼 추출)  │
                  └──────────┬───────────┘
                             │ (교차 검증)
   ┌─────────────────────────┼─────────────────────────┐
   │                                                   │
┌──┴─────────────────────┐                           ┌─┴──────────────────────┐
│  2. 시스템 카탈로그     │                           │  3. EXPLAIN 실행 계획  │
│ (실제 인덱스 & 테이블 크기)│                           │ (옵티마이저의 선택 노드)│
└────────────────────────┘                           └────────────────────────┘

```

#### 1단계. SQL AST 문법 트리 분석 (`sqlglot` 엔진)

- **목적**: 쿼리에서 "필터링(`WHERE`)이나 정렬(`ORDER BY`)에 실제로 사용된 테이블과 컬럼"이 무엇인지 식별합니다.
- **이유**: 단순 정규식이나 문자열 검색은 테이블 별칭(Alias, 예: `orders o` -> `o.user_id`)이나 복잡한 서브쿼리 내의 컬럼을 제대로 짚어내지 못합니다. AST 파서는 이를 트리 구조로 완벽히 쪼개어 `orders` 테이블의 `user_id` 컬럼이 조건절에 쓰였음을 명확히 알아냅니다.

#### 2단계. PostgreSQL 시스템 카탈로그 조회 (`PGMetadataProvider`)

- **목적**: 해당 테이블에 **"실제 어떤 인덱스들이 만들어져 있는지"**, 그리고 **"테이블 크기(Row Count)가 얼마나 큰지"** 확인합니다.
- **이유**: 소량의 데이터(예: 10건)가 들어있는 테이블은 인덱스가 있어도 옵티마이저가 풀 스캔(`Seq Scan`)을 해버립니다. 따라서 카탈로그를 조회해 실제 테이블 규모와 인덱스 컬럼 목록(`user_id`가 인덱스 첫 열로 지정되어 있는지 등)을 파악합니다.

#### 3단계. EXPLAIN 실행 계획 추적 (`PGPlanAnalyzer`)

- **목적**: PostgreSQL 옵티마이저가 실제로 수립한 "물리적 실행 계획"을 받아옵니다.
- **이유**: 아무리 쿼리를 잘 짜고 인덱스가 있어도, 옵티마이저가 엉뚱한 길을 선택할 수 있기 때문입니다. 실행 계획상에 `Seq Scan` 노드가 찍혔는지를 최종 확인합니다.

### 💡 튜닝 제안서가 발행되는 판단 논리 (예시)

이 3가지 정보가 모이면, 휴리스틱 엔진(`PGHeuristicEngine`)이 다음과 같은 스마트한 의사결정을 내립니다.

- **케이스 A (인덱스 누락형 🔴 `CRITICAL`)**
- AST 분석 결과: `orders` 테이블 조건절에 `user_id`가 쓰임.
- 카탈로그 조회 결과: `orders` 테이블에 `user_id`를 포함하는 인덱스가 없음.
- 실행 계획 결과: `Seq Scan` 작동 중.
- **진단**: **"인덱스가 아예 없어서 풀 스캔 중입니다! 인덱스 생성 스크립트 DDL을 드립니다."**

- **케이스 B (통계 정보 불일치형 🟡 `WARNING`)**
- AST 분석 결과: 조건절에 `user_id`가 쓰임.
- 카탈로그 조회 결과: `user_id` 인덱스가 완벽히 실존함. 테이블 크기가 매우 큼(100만 건).
- 실행 계획 결과: 인덱스를 무시하고 `Seq Scan`으로 풀 스캔 중.
- **진단**: **"인덱스가 있는데도 옵티마이저가 풀 스캔을 돌립니다. 테이블 통계가 꼬였으니 `ANALYZE` 명령어로 통계를 갱신하세요."**

- **케이스 C (최적화 완료형 🟢 `INFO`)**
- AST 분석 결과: 조건절에 `user_id`가 쓰임.
- 카탈로그 조회 결과: 인덱스가 있고, 데이터 건수가 아주 작음(50건).
- 실행 계획 결과: `Seq Scan` 작동 중.
- **진단**: **"데이터가 너무 작아 인덱스 탐색 비용이 더 비쌉니다. 풀 스캔이 최적의 선택이므로 그대로 두셔도 됩니다."**

---

이처럼 "구문 분석(AST) + 백엔드 데이터베이스 상태(카탈로그) + 옵티마이저의 결정(Explain)"이라는 3바퀴가 완벽히 맞물려 돌아가기 때문에, 오진 없이 정밀하고 정확한 튜닝 처방전이 나올 수 있는 것입니다.

"디스크 I/O를 유발하는가?" > 1. 인덱스가 없어서 디스크 처음부터 끝까지 다 읽는가? (Seq Scan) 2. 메모리가 부족해서 디스크에 임시 파일을 쓰고 정렬하는가? (External Sort) 3. 적절한 조인 경로가 없어 상대 테이블을 수만 번 반복해서 뒤지는가? (Non-indexed Nested Loop)
